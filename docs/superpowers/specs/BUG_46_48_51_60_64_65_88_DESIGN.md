# BUG-46, BUG-48, BUG-51, BUG-60, BUG-64, BUG-65 and BUG-88 design

## Status

**Implemented and live-verified on 2026-08-11.** Prepared from the repository,
a live Windows-host SQLCipher probe, and current primary documentation for
Claude Cowork, Claude Code, ChatGPT, Codex, OpenClaw and Hermes Agent. The
approved decisions below remain the implementation contract; closure evidence
is recorded as FIXED-171 through FIXED-177 in `docs/plans/FIXED_ITEMS.md`.

## Outcome

Close the seven requested defects without weakening Raiker's owner-authoritative,
fail-closed governance model:

- report database encryption and key-memory locking as separate, proven facts;
- provide a resumable first-run experience and native host control without a
  terminal;
- remove policy configuration that has no runtime effect;
- disclose every governed refusal from the runtime, even if the model omits it;
- make task creation and task execution separate owner decisions;
- make exported citations self-contained without exporting source passages; and
- keep ordinary loopback reads responsive without relaxing public-bind limits.

The implementation also closes BUG-59 because BUG-60 currently repeats its
incorrect **Settings → Capabilities** destination. The shipped destination is
**Permissions**, and keeping the wrong copy while fixing the disclosure path
would preserve a known broken owner instruction.

The remaining GAP-BUILD and GAP-CHAT entries are outside this bug set. This work
must preserve their existing behaviour and tests, but it does not claim to close
the separately itemised feature gaps.

## Architecture and contracts

### BUG-46 — prove or degrade SQLCipher memory protection

The current Windows host runs `sqlcipher3-wheels 0.5.7` with SQLCipher 4.12.0.
At-rest encryption works, but `cipher_memory_security=ON` can terminate the
process with a stack overflow after `VirtualLock` fails. The host also cannot
raise its working-set limits (`SetProcessWorkingSetSize` returns Windows error
1314). The application must therefore discover the posture without risking the
resident server.

Add a `SQLCipherMemoryProbe` with three modes:

- `auto` (new default): run a sacrificial child process against a temporary,
  randomly keyed database. Enable enhanced memory security in the resident
  process only if the child completes a forced crypto workload without a lock
  warning or abnormal exit.
- `on`: require that same proof and refuse startup with a named remediation if
  it fails. An explicit strict operator request must not silently downgrade.
- `off`: keep database encryption enabled, keep enhanced locking disabled, and
  report that choice as degraded rather than healthy.

The probe returns a durable, redacted posture record:

```text
encryption: encrypted | unavailable
memory_lock: locked | degraded | unsupported | unknown
mode: auto | on | off
sqlite_version / sqlcipher_version / driver_version
platform / platform_release
working_set_min_bytes / working_set_max_bytes
probe_exit_code / reason_code / remediation
checked_at
```

No database key, temporary key or raw stderr is persisted. The child receives
its random probe key over an inherited pipe, not argv or an environment
variable. Temporary probe files stay under the workspace runtime directory and
are removed on both success and failure.

`GET /api/health` remains pre-auth and returns only the coarse health state.
The authenticated security-health response carries the detailed posture.
Settings → Security & sign-in adds one compact card with two independent rows:
**Database · Encrypted** and **Key memory · Locked in memory / Degraded**. The
degraded detail includes the detected build, process limit and platform-specific
remediation. **Locked in memory** appears only after a passing proof.

CI runs the probe on the supported Windows release runner and asserts that a
failed lock is classified without taking down the parent. The live Windows
client-host run records the actual result; it is acceptable for that result to
be **Degraded**, but never acceptable to hide or mislabel it.

### BUG-48 — full first run, runnable packages and a native tray

#### First-run state

Evolve `ModelSetupState` into owner-scoped `SetupState` while retaining a
compatibility adapter for `/api/model-setup` during the migration. The state is
resumable and contains only choices that have runtime consumers:

```text
status: required | in_progress | skipped | complete
step: account | model | privacy | backup | finish
model_profile_id / model_name / model_deferred
privacy_acknowledged_at
backup_mode: later | local
backup_target / backup_verified_at
background_service_enabled
created_at / updated_at
```

Every post-account configuration step has **Back** and **Skip for now**. The
owner account itself remains the non-skippable authentication boundary, as it is
in Claude and ChatGPT Desktop; it sits immediately before the authenticated
wizard rather than becoming an optional security control. Skipping the complete
wizard keeps model-backed work behind the existing readiness gate and leaves
backup unset. The existing account-creation screen becomes stage one visually;
after account creation, the wizard opens at the model stage and shows the
account/instance stage as complete.

The five stages are:

1. **Your Raiker** — create or confirm the owner account and name the local
   instance.
2. **Model connection** — choose hosted, Ollama, LM Studio, GGUF or Hugging Face,
   enter credentials through the existing protected Connect dialog, and run the
   exact readiness check. **Decide later** is first class.
3. **Privacy boundary** — explain local versus hosted data flow and the current
   permission mode in plain language. This is an acknowledgement, not a hidden
   policy mutation.
4. **Backup** — choose **Set up later** or a local/removable/NAS directory. A
   local target is saved only after a writable probe and a successful initial
   snapshot through a new backup service. Cloud choices do not render until a
   connector actually implements them. This avoids another dead configuration
   field.
5. **Ready** — summarize the proven model state, privacy boundary, backup result
   and background-service state, offer the same per-user service registration
   used by Host control, then open Workbench.

The backup service writes a host-recoverable encrypted snapshot, using a
dedicated per-instance backup key held by Raiker's protected key store. It
writes a checksum and key-reference manifest atomically, registers it in
`backup_manifests`, and supports **Back up now** from Settings. Portable
cross-host migration remains the separate export workflow. A failed initial
snapshot leaves the target unsaved and offers retry or defer. It never deletes
external backups. The packaged tray can provide a native directory picker;
source/server installs retain a validated path field as the fallback.

#### Visual design

The wizard uses the existing Manrope, Source Serif 4 and JetBrains Mono fonts,
spacing scale, surface tokens, status colors and dark/high-contrast themes. It
is a focused “setup checklist” rather than a generic marketing carousel:

- a narrow left rail shows the five named stages and their proven/deferred state;
- the content pane holds one decision at a time with a short consequence line;
- the footer keeps Back, Skip and Continue in stable positions;
- readiness, privacy and backup summaries use the same chips and cards already
  used by Models and Host controls;
- at 760 px and below the rail becomes a compact horizontal step summary;
- focus order, visible focus, reduced motion and status announcements are part
  of the component contract.

#### Native companion and installers

Add a small `raiker-tray` executable built per release target. A PyInstaller
one-directory build contains Python, Raiker, the built SPA and its runtime
dependencies. `pystray`/Pillow provide the platform-native Windows notification
area, macOS menu-bar and Linux StatusNotifier/AppIndicator backends using the
existing Raiker icon.

The tray is deliberately thin:

- Open Raiker
- Running / Paused / Needs attention (read-only status)
- Pause or Resume
- Restart
- Quit

It does not reimplement lifecycle logic. At service start, Raiker creates a
short-lived random tray bootstrap secret in a user-only runtime file. A
loopback-only exchange consumes it and mints a host-control-scoped session;
the tray then calls the existing `/api/host`, `/pause`, `/resume`, `/restart`
and `/quit` routes. The session cannot read conversations, credentials or
instance data. Secrets never appear in a URL, argv, logs or screenshots.

The current WiX installer only copies the release payload even though the
distribution document says the result is runnable. BUG-48 therefore also adds
the frozen runtime, Start-menu shortcut, per-user background registration and
tray launch to the MSI. The macOS package and Linux artifacts receive the same
frozen runtime/launcher contract. Packaging smoke tests must install into a
temporary per-user prefix, launch the binary without a system Python, open the
health endpoint, observe the tray process, and uninstall without touching
instance data.

### BUG-51 — remove dead policy configuration

Delete `StaticPolicyConfig.denied_actions`. The authoritative static sets stay:
allowed/read-shaped actions and approval-required actions, with `PolicyEngine`
as their only interpreter. Add an invariant test that:

- every registered built-in action has an explicit policy classification;
- no action appears in conflicting sets; and
- no public configuration field exists without a production read site.

This has no UI change. It reduces policy ambiguity rather than changing a
decision.

### BUG-60 and BUG-59 — runtime-owned refusal disclosure

Normalize every broker result before the orchestrator gives it back to the
model. A result with `status=denied` or a governed withheld error emits exactly
one `model_tool_call_refused` stream event even when the outer policy decision
was `allow`. Deduplicate by turn ID plus tool-call ID so an outer policy refusal
and an inner gate refusal cannot produce two cards.

The event contains safe runtime facts only: tool name, call ID, reason code,
safe message, policy/gate source and whether the turn continued. The original
tool result still goes to the model so it can recover or explain. Chat and Build
render the existing refusal card independently of the model's prose.

All model-facing tool-result JSON uses `ensure_ascii=False`; owner-facing text
therefore renders `→` rather than `\u2192`. The web refusal string names the
actual **Permissions** destination and shares its label with navigation metadata
so a later rename cannot drift.

### BUG-64 — create now, run only when asked

Add an explicit execution-intent parameter to `DashboardService.create_task`:

```text
start_immediately: bool = true
```

Human use of Tasks → Plan work retains `true`. Model tool calls and approved
**Create task** proposals pass `false`, producing a queued task with
`scheduled_at = null`. The scheduler already ignores rows without a scheduled
time and must continue to do so.

Add `POST /api/tasks/{task_id}/run` as an owner-scoped action that atomically
sets `scheduled_at` to now only when the task is runnable and unscheduled.
Tasks shows **Ready when you run it** plus **Run now** for that state. The
approval detail says: “Creates one task in Tasks. It will wait until you run or
schedule it.” No scheduler nudge occurs after approval.

### BUG-65 — portable citation ledgers

Extend each assistant `TranscriptMessage` with ordered source metadata loaded
from the existing turn-source ledger:

```text
source_id / title / locator / kind / tool_name
```

Markdown, HTML and PDF put **Sources for this answer** immediately after the
assistant answer when it has citations. Source IDs remain identical to the
markers in the answer. Title and locator pass through the existing export
redactor and HTML escaping. Source passages are never exported.

If an answer contains a marker that has no owner-visible ledger row, remove
that marker from the portable formats and record the count in the export
manifest. The export must never pretend an unresolved marker is a citation.
JSON manifests include the same redacted metadata so format consumers have one
source of truth.

### BUG-88 — separate loopback reads from exposed-host abuse control

Pass an explicit bind posture into `create_app` and `RateLimitMiddleware`.
Safe `GET`, `HEAD` and `OPTIONS` requests bypass the per-IP fixed window only
when both conditions hold:

- the server was configured for loopback-only binding; and
- the request peer is a recognized IPv4 or IPv6 loopback address.

POST/PUT/PATCH/DELETE requests remain limited on loopback. `--allow-public`
keeps the existing 120-request/60-second per-IP bound for every API method,
including a request that happens to originate on the same machine. Proxy
headers do not establish loopback identity.

Tests cover IPv4, IPv6, a spoofed forwarding header, write bursts, public bind
and the ordinary navigation/poll pattern that reproduced BUG-88.

## Error handling and audit rules

- Setup saves after each completed stage and resumes at the first incomplete
  stage after a browser or service restart.
- Provider/auth errors keep credentials masked, retain the form state and show
  the existing reason-code-to-owner-copy mapping.
- Tray control fails closed when its bootstrap secret or scoped session is
  absent, expired or has the wrong file permissions; **Open Raiker** remains
  available when a browser can be opened safely.
- A backup failure never marks setup complete for that target and never leaves
  a partial file under the final backup name.
- Every refused tool call, task start, host lifecycle mutation and backup run
  has a structured audit event with secrets redacted.
- Rate-limit responses keep their current stable reason and retry metadata.

## Test strategy

Implementation follows red-green-refactor in these slices:

1. SQLCipher child-probe classification, strict/auto/off mode and security API.
2. Setup-state migration, stage validation and actual backup consumption.
3. Wizard component accessibility and resume/defer/error states.
4. Frozen runtime/tray authentication, menu actions and packaging smoke.
5. Policy configuration invariant and dead-field removal.
6. Inner-gate refusal event/deduplication plus Unicode transport.
7. Parked task creation, explicit run endpoint and Tasks UI.
8. Source-ledger transcript exports in Markdown, HTML and PDF.
9. Loopback/public rate-limit matrix.

The focused tests are followed by the full Python suite, web unit suite, web
build, Playwright suite, packaging smoke and workflow-equivalent commands.
