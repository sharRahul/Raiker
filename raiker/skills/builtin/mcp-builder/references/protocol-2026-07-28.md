## The one idea

The protocol core became **stateless request/response**. There is no session,
no handshake, and no server-initiated request over a held-open stream. A server
can now sit behind a plain round-robin load balancer, and any request can be
answered by any instance.

Everything below follows from that. If you are porting a server, the work is
almost entirely deleting state you no longer need to keep.

## Every request is self-describing

The `initialize` / `notifications/initialized` exchange and the
`Mcp-Session-Id` header are gone. What the handshake used to establish now
travels in `_meta` on every request:

| `_meta` key | Sent by | Carries |
|---|---|---|
| `io.modelcontextprotocol/protocolVersion` | client | The revision the client speaks |
| `io.modelcontextprotocol/clientCapabilities` | client | What the client supports |
| `io.modelcontextprotocol/clientInfo` | client | Name and version |
| `io.modelcontextprotocol/serverInfo` | server | Name and version, on the response |
| `io.modelcontextprotocol/logLevel` | client | Per-request log level — `logging/setLevel` is gone |

```json
{
  "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": {"name": "search", "arguments": {"q": "otters"}},
  "_meta": {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientInfo": {"name": "my-app", "version": "1.0"}
  }
}
```

OpenTelemetry context propagates through the same `_meta` object using the
standard `traceparent`, `tracestate` and `baggage` keys.

**Consequence for your server:** cross-call state must be explicit. Where you
would once have kept a per-session object, mint a **handle** — an opaque id the
server returns in one tool's result and accepts as an ordinary argument to the
next. It is visible in the schema, it survives a load balancer, and the agent
can see that the two calls are related.

## Discovery replaces the handshake

`server/discover` is mandatory. It advertises supported protocol versions,
capabilities and identity, and it is how a client learns what it is talking to
without opening a session. Implement it first: a server that answers nothing
else still has to answer this.

`ClientCapabilities` and `ServerCapabilities` both gained an `extensions` field,
which is how anything outside the core (tasks, for one) is negotiated.

## Results carry a resultType

Every result now requires `resultType`, one of:

- `"complete"` — the ordinary answer;
- `"input_required"` — the server needs something before it can finish.

A client that does not understand `input_required` will treat the call as
unfinished, so return it only where you mean it.

## Multi round-trip requests

MRTR is the replacement for server-initiated requests. Instead of the server
calling back over a stream, it *returns*:

```json
{
  "resultType": "input_required",
  "inputRequests": [
    {"id": "confirm-delete", "kind": "confirmation",
     "prompt": "Delete 412 records from staging?"}
  ]
}
```

The client then **re-issues the original call** with the answers attached as
`inputResponses`. Two things follow, and both are easy to get wrong:

1. **The retry must be safe.** Your handler will run twice — once producing the
   request, once with the answer. Do the destructive part only on the pass that
   has the response in hand.
2. **Carry no hidden state between the two.** Everything you need on the second
   pass must be in the arguments or in the `inputRequests` you emitted, because
   the retry may reach a different instance.

This is the right place for a destructive operation's confirmation: it is
in-protocol, the client renders it, and the agent cannot satisfy it by asserting
that the user agreed.

## Cacheable list results

`tools/list`, `prompts/list`, `resources/list`, `resources/templates/list` and
`resources/read` return a `CacheableResult`, which requires:

| Field | Meaning |
|---|---|
| `ttlMs` | How long the result may be reused |
| `cacheScope` | Who may reuse it — the shared/per-client distinction |

Set `ttlMs` honestly: too long and a client shows tools you have removed; zero
means "never cache", which costs a round trip on every turn.

Also **return tools in a deterministic order**. A stable order lets clients
cache and materially improves model prompt-cache hit rates; a set iterated in
hash order defeats both.

## Subscriptions replace the GET stream

The HTTP GET endpoint and `resources/subscribe` / `resources/unsubscribe` are
replaced by `subscriptions/listen`: one long-lived POST stream the client opens,
naming the notification types it wants —

`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`,
`resourceSubscriptions`

— with each notification tagged `io.modelcontextprotocol/subscriptionId`.

SSE resumability is gone with it: there is no `Last-Event-ID` and no event ids.
A broken stream means the client re-issues the request in full, so **never treat
a delivered notification as an acknowledgement of anything**.

## Transport headers

Streamable HTTP POSTs must carry:

| Header | Value |
|---|---|
| `MCP-Protocol-Version` | `2026-07-28` |
| `Mcp-Method` | The JSON-RPC method, e.g. `tools/call` |
| `Mcp-Name` | The tool/prompt/resource name |

They exist so a gateway can route, meter and authorise without parsing the body.
If the headers and the body disagree, that is `HeaderMismatch` (`-32020`) — so
generate them from the body rather than writing them twice.

Custom headers travel under `x-mcp-header`.

Error-code allocation is now fixed: `-32000`…`-32019` implementation-defined,
`-32020`…`-32099` reserved for MCP. `MissingRequiredClientCapability` is
`-32021` and `UnsupportedProtocolVersion` `-32022`. Resource-not-found moved
from `-32002` to `-32602` (Invalid Params).

## Authorization

- Authorization servers include `iss` per RFC 9207, and **clients must validate
  it**.
- Client credentials are keyed by issuer and may not be reused across
  authorization servers.
- Dynamic Client Registration (RFC 7591) is **deprecated** in favour of Client
  ID Metadata Documents; where DCR is still used, `application_type` is
  required.

None of this changes the rule that matters most for a server: credentials come
from the environment or the host's vault, never from a tool parameter.

## Tasks became an extension

Long-running work moved out of the core to `io.modelcontextprotocol/tasks`,
negotiated through `extensions`. It is poll-based now: `tasks/get` and
`tasks/update` replace the blocking `tasks/result`, and `tasks/list` is gone.
Model a long job as: start it, return a handle, let the client poll.

## Deprecated and removed

| Feature | State | Do instead |
|---|---|---|
| `initialize` / `notifications/initialized` | Removed | `_meta` on every request; `server/discover` |
| `Mcp-Session-Id` | Removed | Server-minted handles as tool arguments |
| `ping` | Removed | — |
| `logging/setLevel`, `notifications/roots/list_changed` | Removed | `io.modelcontextprotocol/logLevel` in `_meta` |
| `resources/subscribe` / `unsubscribe`, HTTP GET stream | Removed | `subscriptions/listen` |
| `Last-Event-ID`, SSE event ids | Removed | Re-issue the request |
| `notifications/elicitation/complete`, `elicitationId` | Removed | — |
| **Roots, Sampling, Logging** | Deprecated | Do not build new servers on them |
| **HTTP+SSE transport** | Deprecated | Streamable HTTP |
| `includeContext: "thisServer" \| "allServers"` | Deprecated | `"none"`, or omit |
| OAuth DCR (RFC 7591) | Deprecated | Client ID Metadata Documents |

Deprecated features get a minimum twelve-month window before removal, under the
revision's new lifecycle policy (Active → Deprecated → Removed).

Schemas loosened usefully: `inputSchema` and `outputSchema` accept any JSON
Schema 2020-12 keywords, and `structuredContent` accepts any JSON value.

## Migration checklist

For a server written against an earlier revision:

1. Delete session state. Anything that survived between calls becomes an
   explicit handle argument.
2. Implement `server/discover`.
3. Read protocol version, capabilities and client info from `_meta`; stop
   expecting `initialize`.
4. Add `resultType` to every result.
5. Convert any server-initiated prompt or confirmation to MRTR, and make the
   handler safe to run twice.
6. Add `ttlMs` and `cacheScope` to every list/read result, and sort `tools/list`
   deterministically.
7. Convert change notifications to `subscriptions/listen`.
8. Emit `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` from the request
   body, never hand-written.
9. Validate `iss` on tokens; stop relying on DCR.
10. Move long-running work to the tasks extension, poll-based.
11. Re-run the whole verification pass in `SKILL.md` §4 — a migration that
    changes result shapes changes what every tool returns.
